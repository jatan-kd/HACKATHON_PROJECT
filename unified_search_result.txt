            "content": "Use Cases There could be four broad categories for accessing external data in a QUANTUM application: Moment-in-time data, or capturing a snapshot . Capturing data and allowing users to refresh on-demand . Synchronizing data through replication . Performing real-time look-ups with data reference . Data Snapshot (Copy) This feature is already available for masters / global code entities , and for cross-app entities . Useful for capturing fields on flip events (cross-document transitions), which is typically achieved via Lifecycle + transform functions / CLICK mapping. Data gets copied from source to destination document and stored locally. It is the go-to option for capturing contractual or legal-binding information on documents, data that shouldn\u2019t change at later times. Data Refresh On-Demand Useful for keeping local copies of the information on the documents, which in turn can be quickly searched or reported on, but also to refresh the information whenever on-demand (similar to replication, see below). For scenarios where the end-user needs to be in control or where the alternative automatic solutions (see below) are not feasible. Data Replication (Sync) Useful for synchronizing potential updates from sources like masters, global codes, supplier profiles, user info, etc. Such data must be stored locally on documents but it might also get deleted, inactivated, or even updated (in a significant way) at the origin. When this happens, document values should be updated accordingly. Examples : A project gets assigned to category \u201cACCOUNTING SOFTWARE\u201d and this category name gets an update, the project must reflect the new name. Master data like CBR or global codes (purchase type) gets rarely updated but it would impact transactional data ER-11908 - Getting issue details... STATUS Example: Supplier is deleted or someone revokes its approval for a particular buyer), it would help to mark the references as \u201cdirty\u201d (outdated/inactive) on S2P documents. A user goes inactive and multiple documents are referring this user. All sensitive data of an inactive user must be anonymized at some point in time. Sync between Collab construct and TPRM: NCMDS-10534 - Getting issue details... STATUS Data Reference (Virtual) Referenced data will not be stored on documents, but must be fetched every time it gets displayed along with the documents or when it needs to be evaluated/validated in some way. Examples : Contract Manager to be validated on Requisition submit, but not stored on Req. When adding the Contract to Req, an approval rule is triggered on submit of Req, and will go to different approvers depending on the contract manager. Same contract manager is also used in Invoice via rules. While configuring business/approval rules, the user wants to validate values of cross-app references, so they must be able to select them from while configuring a condition or the output of the rule. There are several examples showcased on this spreadsheet , including sources such as CMDS, UM, App-specific APIs. Email notifications will send document data along with referenced data from suppliers such as the current supplier name or status. TPRM form has the very latest name of say a Purchase Order, or Supplier. The \u201csupplier name\u201d should always be the updated one, so the data values must come from the source app. Option to open up the iCard for a supplier with the latest info. Solution Proposal Platform to support different mechanism that offer developers flexibility: Snapshot of the source data captured on the consumer documents (already supported). This will copy the data on the consumer side and will keep a reference-in-time that won\u2019t get any updates. On-Demand Refresh will use a model that provides the speed of a local copy but the on-demand accuracy of a real-time lookup, while giving control to the user. Replication will sync (propagate) data updates to consumers. Reference will always get the latest data from the source with real-time lookups. Click to see the Benefits and Challenges for each method Method Useful for Benefits Challenges Snapshot (composition) Historically accurate references, i.e. capturing \u201cmoment in time\u201d data. Preserving historical, legal, and financial integrity. Capturing fields on flip events (achieved via Lifecycle + transform functions / CLICK mapping). Already supported. Minimal load on the system. Data services required only when transactional records get created. Consumer data doesn\u2019t get impacted, so it can be pulled frequently or rarely, doesn\u2019t matter. Solid searching & reporting capabilities. Somewhat more storage used for transactional data. No real-time or even eventual-consistent data. On-Demand Refresh Gives end-users control to retrieve real-time data when necessary. Provides the speed of a local copy but the on-demand accuracy of a real-time lookup. Small load on the system. Data services required only when user wants to fetch the latest data (discretionary). Partial searching & reporting capabilities. On-demand accuracy & consistency of data. Searching or reporting might return a mix of outdated and up-to-date data. Somewhat more storage used for transactional data. A more complex approach (combination of other mechanisms). Replication (sync) Consumer data needs to be updated but it is not time-critical. Source data changes rarely. Consumer data is accessed (pulled) frequently. Master data/global codes updates. Supplier profiles updates. User goes inactive. User data anonymization. Eventual-accuracy & consistency of data. This framework can solve other use cases (anonymization, disposal). Flexibility based on business needs (don\u2019t update Contract that is expired). Solid searching & reporting capabilities. Performance toll on the system to propagate data changes. Ingestion pipeline can get busy. No realtime data, slower than ES. Somewhat more storage used for transactional data. Reference (virtual) Realtime use cases. Source data changes frequently. Consumer data is accessed (pulled) rarely. Certain document updates that depend on particular user actions, such as changing the Supplier on an Order should fetch and update the ERP IDs, Tax Info, etc. Evaluating conditions on business/approval rules or for workflows/BPM processes. Showing more info on an iCard / partial view. Data accuracy & consistency. Ingestion pipeline not affected. Minimal storage required for transactional data. Performance toll on every read. Searching becomes limited. Reporting becomes limited. User Journey Application Developers / TSO Define your external data structures in Domain Model [ Preferred ] Import any master, global codes , or a cross-app entity into your domain model. Associate these structures with your other application entities, as needed. Note: when a new field gets added on the source, simply re-import the entity in your application to make the new field available. [Alternative] Map your existing custom entities with the standard master, global codes, or cross-app entities that are recognized by the platform. Update your entity type = Master / Cross-Application. Use the mapper feature to correlate your custom fields (on the left) to standard fields on the source master/cross-app entity (on the right). Note: when a new field gets added on the source, add an equivalent field in your custom entity and reconfigure the mapper to make the new field available in your app. Configure the expected behavior for each field (property): Snapshot (Copy) - this is the default option On-Demand Refresh Replication (Sync) Reference (Virtual) For \u201cReplication (Sync), user can further customize the action or the scope as needed: Set the action via Kamunda or Jobs interface. Source field value updated \u2192 Destination field value updated to match (default) Source field value updated \u2192 Destination field value marked as outdated Source object deleted \u2192 Destination field value marked as outdated (default) Source object deleted \u2192 Destination field value deleted Source object deleted \u2192 Destination object marked for disposal Set conditions by picking a dataset for narrowing down the applicability. Example: only update contracts that have not expired and are of the latest version. End-User Snapshot (Copy) fields May take a default value (e.g. payment term on purchase order), but user could overwrite. May also be read-only. The values of these fields will NOT change regardless of any updates to external data, until and unless the user updates them on the particular document. Documents could obviously be searched or filtered by such values. On-Demand Refresh fields User gets a \"Refresh\" button next to the field (or for the whole form) to get the latest values, but at the same time use search, filter, or create reports for such fields. Replication (Sync) fields User may update a category name or a supplier name and after a while, see this reflected on multiple projects, RFXs, etc. If a Supplier Profile gets deleted or revoked, user would recognize this on related documents by seeing \u201c<Supplier Name> (decommissioned)\u201d / using an icon or tooltip. Note: if the user tries to submit a form with outdated data, a warning banner/message should be used. When a specific \u201cpurchase type\u201d gets updated to a new name, users can find documents having this particular purchase type on the workbench or globally. An admin might anonymize a user\u2019s info and this would be reflected on all documents that mention that user\u2019s name or email. Searching, filtering, or reporting by such fields might also return some outdated data, while the synchronization is in progress. Reference (Virtual) fields Values are retrieved every time the user opens up the document detail or the workbench page. On failure to fetch field values (e.g. Supplier is down/slow/etc.) display \"Data Unavailable\" with a \"Retry\" button. Admins can use such fields to create business or approval rules (add as conditions etc.) User cannot search, filter, or create reports for such fields on documents. Solution Design Considerations Overall approaches: Snapshot data = composition. On-demand data refresh = cached references. Replication = publisher-subscriber model + bulk updates. Reference data = virtual entities or DTOs. On-Demand Refresh Replication (Sync) The mechanism to publish the updates based on implicit triggers (Kafka events on specific topic). The subscriber is based on customizable handlers . Platform to offer customization options to a certain degree: conditions on source data, destination data, and action customization. To limit the number of fields that can be used with replication. Running a bulk update processes: Must use a bulk operation - the subscriber should receive one event (supplier-123 updated) and translate it into one bulk update (e.g. update POs with supplierName = x where supplierId = 123). When source data gets deleted, remove the indexed data on consumer app so it won\u2019t match for document searches. Example: if the category \u201celectronics\u201d has been deleted, when searching/filtering by this keyword, user should not find any TPRM documents that had this reference. Audit log should capture such data updates (propagate details from source to destination: updatedBy, updatedOn) Data retention & disposal mechanism can be used to mark as eligible certain documents upon data replication (sync). Same for the user data anonymization mechanism. Open points: How to handle linked references? Example: if Contract replicates Supplier, but Supplier references supplierStatus (global code), what happens? For example, enforce that replicated entities are \"flattened\" at the time of replication (i.e., the supplierStatus is also copied). Can we use OpenSearch (in conjunction with datasets) to do a reverse search and find all impacted documents when e.g. a Supplier changes? Do we need any monitoring of bulk jobs for users/admins? Notifications for completing the update job for a particular update? Reference (Virtual) Extend DM runtime so data lookups can implemented via subtype engine. To limit the number of fields that can be used with lookups. For workbenches, can platform perform batch retrieval? I.e. fetch x number of contracts, gather all unique \u2018supplierIds\u2019, and make one batch API call to get all supplier referenced data at once? Recommended Configurations Thumb rules: Transactional data should heavily rely on \u201cSnapshot (Copy)\u201d to reduce system load and to preserve historical, legal, and financial integrity. If you need to search/filter/report on it, then use \u201cSnapshot(Copy)\u201d or \u201cReplication (Sync)\u201d. If you need accuracy but not necessarily real-time, or if the updates to the masters/global codes can be done outside of business hours, then \u201cReplication (Sync)\u201d is the best option. Instead, if 100% real-time accuracy is key, you must use \u201cReference (Virtual)\u201d and accept that users can't easily search or report on it. High-volatility, non-critical data is feasible for \u201cOn-Demand Refresh\u201d. High-volatility, critical data must use \u201cReference (Virtual)\u201d.
